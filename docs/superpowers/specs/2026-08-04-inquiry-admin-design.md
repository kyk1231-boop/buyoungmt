# 견적문의 접수·관리 시스템 설계

작성일 2026-08-04 · (주)부영미트 홈페이지

## 1. 배경

홈페이지 배포를 앞두고 있다. 견적 문의가 들어오면 사장님 두 분이 알림을 받고, 누가 어디까지 응대했는지 관리할 수단이 필요하다.

## 2. 지금 무엇이 문제인가

견적 폼(`inquiry.html`)은 제출 시 `mailto:` 링크를 열어 **방문자 본인의 메일 앱**에 초안을 띄운다. 방문자가 직접 보내야만 도착한다.

여기서 두 가지가 깨진다.

1. **서버를 거치지 않으므로 알림을 보낼 지점이 없다.**
2. **메일 앱을 연 뒤 0.7초 후 무조건 "접수 완료" 화면을 띄운다**(`inquiry.html:449`). 방문자가 메일을 보내지 않아도 완료됐다고 표시된다. 휴대폰에서 메일 앱이 설정되지 않은 경우가 흔한데, 그러면 방문자는 접수됐다고 믿고 회사는 아무것도 받지 못한다.

문의를 놓치지 않는 것이 이 작업의 첫째 목적이다.

## 3. 범위

**포함**

- 견적 폼을 서버로 전송하고 데이터베이스에 저장
- 저장 성공이 확인된 경우에만 완료 화면 표시, 실패 시 전화 안내
- 사장님 두 분에게 이메일 알림
- 관리자 페이지: 문의 목록, 상태·처리자 변경, 수동 삭제
- 스팸 유입 차단
- 개인정보처리방침을 실제 운영과 일치하도록 수정

**제외** (필요해지면 그때 만든다)

- 견적서 자동 발행, 매출 통계, 고객 등급 관리, 파일 첨부
- 개인 계정 로그인 (공용 비밀번호 1개로 운영)
- 자동 삭제 (아래 10절 참조)

**후속 단계** — 문자 알림은 도메인 연결과 발신번호 등록 후 별도로 붙인다. 이 설계의 구조를 바꾸지 않는다.

## 4. 시스템 구성

```
방문자 → 견적 폼 ─ POST /api/inquiry ─→ 데이터베이스(서울)
                                    └→ 이메일 알림 2통

사장님 → /admin ─ 비밀번호 ─→ 목록 조회 · 상태 변경
```

| 구성 요소 | 선택 | 이유 |
|---|---|---|
| 호스팅 | Vercel (무료) | 정적 페이지와 서버 기능을 한 곳에서 운영. 도메인 없이 임시 주소로 즉시 가동 |
| 데이터베이스 | Supabase Postgres **서울 리전** (무료) | 개인정보를 국내에 저장해 국외이전 고지 의무를 피한다 |
| 이메일 발송 | Resend (무료) | 서버리스 환경에서 SMTP보다 안정적 |

**검증 항목** — 무료 한도와 서울 리전 제공 여부는 구축 착수 시 실제로 확인한다. 조건이 맞지 않으면 Cloudflare Pages + D1 조합으로 대체하며, 이 경우에도 아래 데이터 모델과 화면 설계는 그대로 쓴다.

## 5. 데이터 모델

`inquiries` 테이블 한 개.

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | uuid | 기본키 |
| `created_at` | timestamptz | 접수 시각 |
| `status` | text | `new` / `contacted` / `quoted` / `closed` |
| `handler` | text | 처리자. 미지정 가능 |
| `company` | text | 업체명 (필수) |
| `business_type` | text | 업종 |
| `contact_name` | text | 담당자 성함 (필수) |
| `phone` | text | 연락처 (필수) |
| `cuts` | text[] | 관심 부위 |
| `volume` | text | 월 예상 물량 |
| `packing` | text | 희망 포장 |
| `trim` | text | 손질 요청 |
| `region` | text | 배송 지역 |
| `message` | text | 요청 사항 |
| `sample` | boolean | 샘플 신청 여부 |
| `agreed_at` | timestamptz | 개인정보 수집 동의 시각. 분쟁 시 증빙 |
| `updated_at` | timestamptz | 상태 마지막 변경 시각 |

필드는 현재 폼(`inquiry.html`)의 입력 항목과 일치시킨다. 폼에 없는 항목은 만들지 않는다.

데이터베이스 접근은 서버 기능에서만 한다. 브라우저에서 데이터베이스로 직접 붙지 않는다.

## 6. 화면

### 견적 폼 (기존 `inquiry.html` 수정)

디자인과 입력 항목은 그대로 두고 제출 동작만 바꾼다.

- 제출 → 서버 응답 대기 (버튼은 대기 상태 표시)
- **성공** → 기존 완료 화면
- **실패** → "전송에 실패했습니다. 전화로 연락 주세요"와 함께 `010-4017-1231`, `010-4404-0731`을 크게 표시. 입력한 내용은 지우지 않는다

### 관리자 페이지 (`/admin`)

휴대폰에서 보는 것을 기본으로 만든다. 좁은 화면에서는 카드, 넓은 화면에서는 표로 전환한다. 색과 서체는 홈페이지와 같게 한다.

- **로그인** — 비밀번호 입력 한 칸
- **목록** — 최신순. 상단에 `전체 / 신규 / 진행중 / 종료` 필터와 신규 건수 표시
- **한 건 펼치기** — 전체 입력 내용. 연락처는 눌러서 바로 전화 걸기(`tel:` 링크)
- **상태 변경** — `신규 / 연락함 / 견적발송 / 종료` 선택 즉시 저장
- **처리자 선택** — 사장님 두 분 중 선택. 계정을 나누지 않아도 중복 응대를 막는다
- **삭제** — 건별 수동 삭제. 확인 후 완전 삭제
- **비밀번호 변경** — 현재 비밀번호 확인 후 변경

## 7. 서버 기능

| 경로 | 동작 |
|---|---|
| `POST /api/inquiry` | 입력 검증 → 저장 → 이메일 발송 → 결과 응답 |
| `POST /api/admin/login` | 비밀번호 확인 → 세션 쿠키 발급 |
| `POST /api/admin/logout` | 세션 종료 |
| `GET /api/admin/inquiries` | 목록 조회 (상태 필터) |
| `PATCH /api/admin/inquiries/:id` | 상태·처리자 변경 |
| `DELETE /api/admin/inquiries/:id` | 삭제 |
| `POST /api/admin/password` | 비밀번호 변경 |

`/api/admin/*`는 유효한 세션 없이는 모두 거부한다.

이메일 발송이 실패해도 저장이 성공했으면 방문자에게는 성공으로 응답한다. 문의를 잃지 않는 것이 알림보다 우선이다. 발송 실패는 서버 로그에 남긴다.

## 8. 알림

접수 즉시 사장님 두 분 이메일로 발송한다.

- 제목: `[견적요청] {업체명}`
- 본문: 접수 시각, 전체 입력 내용, 관리자 페이지 링크

수신 주소는 설정값(환경변수)으로 둔다.

| 수신자 | 이메일 |
|---|---|
| 배명운 대표이사 | `siaabba@naver.com` |
| 김유경 상무 | `kyk12318638@naver.com` |

처리자 선택 목록도 같은 두 사람으로 한다: `배명운 대표이사`, `김유경 상무`.

## 9. 보안

- 비밀번호는 해시로 저장한다. 평문으로 두지 않는다. 값은 환경변수로만 주입하며 저장소나 문서에 남기지 않는다
- 세션은 서명된 HttpOnly 쿠키로 관리한다. 유효기간 30일
- 로그인 실패가 반복되면 일시 차단한다 (5회 실패 시 15분)
- 관리자 페이지에서 비밀번호를 변경할 수 있게 한다

**초기 비밀번호에 관한 판단** — 사용자가 지정한 초기값은 네 자리 숫자다. 조합이 1만 가지뿐이라 자동 대입에 약하지만, 위 실패 차단(5회 / 15분)을 적용하면 전부 시도하는 데 수백 시간이 걸려 실질적 방어가 성립한다. 그럼에도 고객 개인정보를 다루는 화면이므로 가동 직후 더 긴 비밀번호로 변경할 것을 권고한다. 변경 기능을 1단계에 포함하는 이유다.
- `/admin`은 검색엔진에 노출되지 않게 막는다 (`robots.txt` 및 `noindex`)
- 통신은 전 구간 HTTPS
- 스팸 차단: 보이지 않는 함정 입력칸과 최소 작성시간 검사. 무작위 봇은 대부분 걸러진다. 부족하면 그때 추가 장치를 붙인다

공용 비밀번호 방식은 누가 상태를 바꿨는지 기록되지 않는다는 한계가 있다. 처리자 선택으로 실무상 보완하며, 두 분만 쓰는 상황을 전제로 수용한다.

## 10. 개인정보 처리

**보유 기간: 무제한** (사용자 결정, 2026-08-04). 자동 삭제 기능은 만들지 않는다. 삭제는 관리자 페이지에서 수동으로 한다.

이 결정에는 법적 위험이 따른다. 개인정보보호법은 수집 목적이 달성되면 지체 없이 파기하도록 정하고 있어, 견적 문의 단계에서 받은 성함과 연락처를 기한 없이 보관하는 것은 정당화가 어렵다.

**따라서 다음을 반드시 함께 수행한다.**

1. `privacy.html`의 보유 기간 항목을 실제 운영과 일치시킨다. 현재 "상담이 종료되고 이용 목적이 달성되면 지체 없이 파기"로 되어 있는데, 이 문구를 그대로 두고 무기한 보관하면 방침 위반이 된다
2. 수집 항목에 저장 위치(국내 클라우드)를 명시한다
3. 정보주체가 요청하면 즉시 삭제한다는 절차를 명시하고, 관리자 페이지의 수동 삭제로 이행한다

**대안 (사용자 미채택, 재검토 여지 있음)** — 종료 후 일정 기간이 지나면 담당자 성함과 연락처만 삭제하고 업체명·부위·물량은 남기는 방식. 기록은 보존되면서 남는 데이터는 개인정보에 해당하지 않게 되어 위 위험이 사라진다.

## 12. 진행 순서

1. **1단계** — 폼 접수, 데이터베이스, 이메일 알림, 관리자 페이지. 임시 주소(`*.vercel.app`)로 가동해 실제로 확인한다
2. **2단계** — 아이네임즈 도메인 연결
3. **3단계** — 문자 알림 추가 (발신번호 사전등록 필요)
